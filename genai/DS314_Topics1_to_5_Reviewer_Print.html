MODULE 1: Foundational AI Taxonomy & Historical Evolution (Topic 1)

1. Academic Context & Theoretical Deep Dive

1.1 The Fundamental Shift: Deterministic Automation vs. Probabilistic AI

Traditional computing relies strictly on deterministic automation: given an explicit set of logical inputs $X$, a hardcoded subroutine $f(X)$ computes an exact output $Y$. If an unanticipated edge case appears, the system crashes or exhibits catastrophic failure.

💡 Intuitive Analogy: The Vending Machine vs. The Adaptive Mind
A vending machine is deterministic automation. When you insert 20 pesos and press B4, a motor mechanically spins a coil. It does not "understand" hunger or chips. If you insert a bent slug or foreign coin, the machine jams. Artificial Intelligence (AI), by contrast, operates under probabilistic pattern recognition: it learns an approximation function $f_\theta(X) \approx Y$ parameterized by learned weights $\theta$, allowing it to generalize across novel, unseen, and ambiguous real-world inputs.
+-----------------------------------------------------------------------------------------+ | AI SYSTEM TAXONOMY | +-----------------------------------------------------------------------------------------+ | [ ARTIFICIAL INTELLIGENCE ]: Computational systems mimicking human cognitive faculties | | | | | +--> [ MACHINE LEARNING ]: Statistical optimization on empirical tabular/feature data| | | | | +--> [ DEEP LEARNING ]: Multi-layered artificial neural networks (ANNs, CNNs)| | | | | +--> [ GENERATIVE AI ]: Models generating novel, high-dimensional data | | | | | +--> [ LARGE LANGUAGE MODELS (LLMs) ]: Transformer-based NLP | +-----------------------------------------------------------------------------------------+

1.2 Mathematical Foundations: Discriminative AI vs. Generative AI

The mathematical distinction between Discriminative and Generative AI lies in the probability distributions they model:

  • Discriminative AI: Models the conditional probability distribution $P(Y \mid X)$—the probability of a label or class $Y$ given an observed input $X$. Its objective is classification, boundary separation, or regression: $$\hat{y} = \arg\max_y P(Y = y \mid X)$$ Example: Given an incoming email $X$, determine whether $Y = \text{Spam}$ or $Y = \text{Not Spam}$.
  • Generative AI: Models the joint probability distribution $P(X, Y)$ or the marginal distribution $P(X)$. Its objective is to capture the underlying data distribution so that it can sample and synthesize brand-new data instances $\tilde{x} \sim P(X)$: $$\tilde{x} \sim P(X \mid C)$$ Example: Given a prompt condition $C$, generate a brand-new customer support email response.
Dimension Discriminative AI Generative AI
Mathematical Goal Models $P(Y \mid X)$ (Decision boundaries) Models $P(X, Y)$ or $P(X)$ (Data distributions)
Primary Task Classification, Detection, Regression Synthesis, Completion, Transformation
Input / Output High-dimensional input $\rightarrow$ Low-dimensional label Prompt / Condition $\rightarrow$ High-dimensional output
Representative Models SVM, Logistic Regression, ResNet, XGBoost GPT-4o, Gemini 2.0, Claude 3.5, Stable Diffusion
Primary Failure Mode Misclassification, Out-of-Distribution Error Hallucination, Mode Collapse, Semantic Drift

1.3 The 4 Industry Operational Layers

Modern enterprise AI is organized into four distinct horizontal layers. Understanding these boundaries prevents architectural confusion between hardware suppliers, model providers, and application developers:

+-------------------------------------------------------------------------------------------+ | LAYER 4: APPLICATION LAYER | | Purpose-built business solutions (GitHub Copilot, Cursor, Notion AI, Duolingo Max, bots) | +-------------------------------------------------------------------------------------------+ ▲ (APIs, SDKs, Middleware) +-------------------------------------------------------------------------------------------+ | LAYER 3: ORCHESTRATION & TOOLING LAYER | | Frameworks connecting models to data & tools (LangChain, LangGraph, LlamaIndex, ChromaDB) | +-------------------------------------------------------------------------------------------+ ▲ (Model Endpoints, Weights) +-------------------------------------------------------------------------------------------+ | LAYER 2: FOUNDATION MODEL LAYER | | Massive pre-trained multimodal models (Google Gemini 1.5/2.0, OpenAI GPT-4o, Claude 3.5) | +-------------------------------------------------------------------------------------------+ ▲ (Compute Hardware & Silicon) +-------------------------------------------------------------------------------------------+ | LAYER 1: HARDWARE & SILICON INFRASTRUCTURE | | Accelerators, supercomputing clusters (NVIDIA H100/B200, Google TPUs, AWS Trainium) | +-------------------------------------------------------------------------------------------+
💡 The Car Analogy: Model vs. Application
Think of the foundation model (Layer 2) as a high-performance car engine. Sitting on a factory floor, the engine is powerful, but an ordinary driver cannot use it to commute. The car itself (Layer 4)—the steering wheel, seats, brakes, and dashboard—is the application built around the engine. Industry Reality: Less than 1% of data scientists will ever train a foundation model from scratch (Layer 2). Over 95% of high-value industry roles focus on Layer 3 and Layer 4: orchestrating, grounding, and integrating models into real-world applications.

1.4 General-Purpose vs. Purpose-Built Applications

  • General-Purpose (e.g., ChatGPT, Gemini Web UI): Broad, open-ended conversational interface. Capable of drafting poems, summarizing articles, or explaining history, but possesses zero access to private company databases or custom workflows.
  • Purpose-Built (e.g., GitHub Copilot, Duolingo Max, Smart/Globe Billing Bot): Narrow, deeply embedded inside a specific application. Equipped with custom system instructions, proprietary company databases, and execution tools. Example: A Globe Telecom billing bot would perform poorly at writing sonnets, but it is vastly superior to ChatGPT at checking your live SIM card data balance because it connects to real billing APIs.

1.5 Evolution of NLP & The Transformer Self-Attention Breakthrough

Before 2017, NLP relied on Recurrent Neural Networks (RNNs) and LSTMs. RNNs processed text sequentially, token-by-token. This created two insurmountable bottlenecks:

  1. Sequential Bottleneck: Computing token $t$ strictly required hidden state $h_{t-1}$. Training could not be parallelized across GPUs.
  2. Vanishing Gradient Problem: Gradients decayed exponentially over long sequences, causing the network to forget instructions from earlier paragraphs.

In 2017, Vaswani et al. published "Attention Is All You Need", introducing the Transformer. By eliminating recurrence and using Self-Attention, all tokens attend to each other simultaneously in $O(1)$ sequential operations, unlocking massive distributed GPU training.

💡 Intuitive Analogy: The YouTube Search (Query, Key, Value)
Self-Attention works exactly like a modern search engine:
  • Query ($Q$): What you type into the search bar (e.g., "how to replace bicycle pedals").
  • Key ($K$): The titles, tags, and descriptions of every indexed video on YouTube.
  • Value ($V$): The actual video content you stream.
Your Query is compared against all Keys via a dot product to calculate relevance scores (attention weights). These weights determine how much of each video's Value is blended into your final answer.
⚠️ High-Yield Exam Trap: Why Divide by $\sqrt{d_k}$?
The Scaled Dot-Product Attention formula is: $$\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V$$ Why scale by $\frac{1}{\sqrt{d_k}}$? In high dimensions ($d_k = 64, 128$), the dot products $QK^T$ grow very large in magnitude. Feeding large values into the $\text{softmax}$ function pushes it into extreme regions where its derivative is virtually zero ($\approx 0$). This causes vanishing gradients during backpropagation! Scaling by $\sqrt{d_k}$ preserves unit variance ($\sigma^2 = 1$) and stabilizes training.

2. Key Definition Glossary (Topic 1)

  • Autoregressive Generation: Next-token prediction where each emitted token $w_t$ is appended to the context for predicting $w_{t+1}$.
  • Context Window: The maximum token capacity (prompt + output) an LLM can process in a single forward pass.
  • Software 3.0: Programming computational behavior through natural language prompts and empirical datasets rather than deterministic logic.
  • Hallucination: Plausible-sounding, syntactically fluent, but factually fabricated model outputs.

MODULE 2: Building with LLMs & RAG Architectures (Topic 2)

1. Academic Context & Theoretical Deep Dive

1.1 The Enterprise Problem: Why Base LLMs Cannot Stand Alone

Deploying a raw foundation model in an enterprise fails due to three major barriers: (1) Knowledge Cutoffs (unaware of events post-training), (2) Private Data Isolation (cannot see internal company records), and (3) Hallucination Risk (fabricates answers when uncertain).

1.2 Fine-Tuning vs. Retrieval-Augmented Generation (RAG)

When should an enterprise fine-tune a model, and when should it build a RAG pipeline?

1.3 The 5-Stage Production RAG Architecture

RAG decouples reasoning (handled by the LLM) from memory (handled by an external vector database):

[ Unstructured Documents: PDFs, Manuals ] │ ▼ [ Stage 1: Ingestion ] ──────────▶ PyPDFLoader / TextLoader │ ▼ [ Stage 2: Chunking ] ───────────▶ RecursiveCharacterTextSplitter (chunk_size=500, overlap=100) │ ▼ [ Stage 3: Embedding ] ──────────▶ Vector Embedding Model (e.g., gemini-embedding-001) │ ▼ [ Stage 4: Storage ] ────────────▶ Vector Store Indexing (ChromaDB, FAISS) │ │ ◄─── User Query: "What is Jollibee's breakfast policy?" ▼ [ Similarity Search ] ───────────▶ Cosine Similarity / Approximate Nearest Neighbors (ANN) │ ▼ Top-K Chunks [ Stage 5: Generation ] ─────────▶ Prompt Template + Grounded Context ──▶ Grounded LLM Response

1.4 Step-by-Step Technical Execution

  • Stage 1: Document Loading: Parsing PDFs, Markdown, or HTML files into text objects with metadata (file path, page number).
  • Stage 2: Chunking & Chunk Overlap:
    ⚠️ Critical Concept: Why Chunk Overlap is Mandatory
    If you split text with chunk_overlap = 0, critical sentences that span across split boundaries get severed in half! For example: "Refunds are granted only if... [CHUNK SPLIT] ...the receipt is shown within 7 days." Chunk 1 says refunds are granted; Chunk 2 contains conditions with no context. Setting chunk_overlap = 100 ensures continuity across boundaries.
  • Stage 3: Dense Vector Embeddings: Mapping text chunks into a continuous high-dimensional geometric space (e.g., 768 or 3,072 dimensions). Concepts with similar meanings cluster together regardless of exact phrasing (e.g., "chicken" and "poultry").
  • Stage 4: Vector Similarity Search: $$\text{Cosine Similarity}(A, B) = \frac{A \cdot B}{\|A\| \|B\|} = \frac{\sum A_i B_i}{\sqrt{\sum A_i^2}\sqrt{\sum B_i^2}}$$ Values range from $-1.0$ (opposite) to $0.0$ (orthogonal) to $1.0$ (identical semantic meaning).
  • Stage 5: Grounded Prompting & Negative Constraints: Injecting top-$K$ chunks into a rigid prompt template requiring the LLM to answer strictly from the text and admit ignorance if missing.

MODULE 3: LangChain Models, Stateful Memory & Autonomy Levels (Topic 3)

1. Academic Context & Theoretical Deep Dive

1.1 Why LangChain? The Orchestration Abstraction

Writing raw HTTP REST API calls to LLMs is brittle. LangChain standardizes the interaction between Models, Prompt Templates, Output Parsers, and External Tools into modular, swappable components.

1.2 Model I/O & The Chat Message Abstraction

  • LLMs vs. Chat Models: Base LLMs take a raw string and output a raw string. Chat Models (e.g., ChatGoogleGenerativeAI) consume structured message objects:
    • SystemMessage: Defines persona, instructions, and negative constraints.
    • HumanMessage: Represents the user's prompt.
    • AIMessage: Represents previous model outputs.
⚠️ Common Student Trap: The AIMessage Return Object
Invoking a LangChain Chat Model (model.invoke("Hello")) does not return a Python string! It returns an AIMessage object containing .content and token usage metadata. To obtain a clean string directly, you must pipe the model into StrOutputParser()!

1.3 LangChain Expression Language (LCEL)

LCEL provides a clean, declarative pipe syntax (|) modeled after Unix pipelines: 

from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_google_genai import ChatGoogleGenerativeAI

prompt = ChatPromptTemplate.from_template("Summarize {topic} in one sentence.")
model = ChatGoogleGenerativeAI(model="gemini-1.5-flash")
parser = StrOutputParser()

# Declarative LCEL Pipeline
chain = prompt | model | parser
result = chain.invoke({"topic": "RAG Architectures"})

1.4 Managing Conversation Memory in a Stateless World

LLM APIs are completely stateless: each HTTP call knows nothing about previous messages. Client applications must maintain and pass conversation history:

  • ConversationBufferMemory: Passes the entire conversation history verbatim. Perfect recall, but token costs explode over time.
  • ConversationBufferWindowMemory(k=N): Passes only the last $N$ turns. Fixed token budget, but loses long-range facts.
  • ConversationSummaryMemory: Periodically prompts a background LLM to summarize past turns into a concise paragraph, retaining context while minimizing tokens.

1.5 The 5 Cognitive Autonomy Levels (High-Yield Core)

Level Designation Operational Architecture & Real-World Example
Level 0 Direct Prompt (No Autonomy) Single input $\rightarrow$ single output. Completely reactive; no tools, no memory. (e.g. Asking ChatGPT a one-off definition).
Level 1 Chained Pipeline (Static Execution) Linear execution sequence (Prompt $\rightarrow$ LLM $\rightarrow$ Parser). Deterministic; cannot dynamically branch.
Level 2 Grounded Retrieval (RAG) System dynamically queries external vector memory to fetch relevant chunks before answering. (e.g. Jollibee FAQ bot).
Level 3 Tool-Using & Function Calling Model dynamically decides which external tool to invoke based on docstrings. (e.g. invoking calculate_vat(price)).
Level 4 Autonomous Agents (ReAct Loop) Iterative ReAct loop: Thought $\rightarrow$ Action $\rightarrow$ Observation $\rightarrow$ Thought. Detects errors and self-corrects.
Level 5 Multi-Agent Swarms Multiple specialized agents (Researcher, Coder, Critic) collaborating and supervising each other via LangGraph.

MODULE 4: Enterprise Prompt Engineering & Decoding Thermodynamics (Topic 4)

1. Academic Context & Theoretical Deep Dive

1.1 The Prompt Anatomy Ladder (V1 $\rightarrow$ V2 $\rightarrow$ V3)

In production software engineering, prompts are not casual text; they are formal specifications that constrain an autoregressive probability distribution:

[ V1: Raw Task Only ] ──▶ "Classify review: Food took forever but burger was good." │ High variance, conversational chatter ("Sure! Here is your answer:...") ▼ [ V2: Task + Role + Context + Target Format ] │ "You are a QA auditor. Classify the review as: POSITIVE, NEGATIVE, or MIXED." │ Better alignment, but still prone to extraneous markdown or explanations. ▼ [ V3: V2 + Programmatically Verifiable Hard & Negative Constraints ] │ HARD CONSTRAINTS: │ 1. Output EXACTLY ONE word from [POSITIVE, NEGATIVE, MIXED]. │ 2. DO NOT include explanations, greetings, punctuation, or markdown. │ 3. Any extra character breaks automated ingestion. ▼ Directly ingestible by automated backend pipelines with 0% format failure.

1.2 In-Context Learning: Zero-Shot vs. Few-Shot

  • Zero-Shot: Providing instructions without examples. Excellent for straightforward tasks on modern capable models.
  • Few-Shot: Providing 2 to 5 worked exemplars inside the prompt. Drastically reduces format errors and guides edge-case classification logic.
  • Error Taxonomy:
    • Content Error: The model hallucinates facts or misclassifies an edge case.
    • Format Error: The classification is correct, but the model injects conversational padding that breaks JSON parsers.

1.3 Decoding Thermodynamics & Sampling Mathematics

Before emitting a token, an LLM outputs raw, unnormalized scores called logits ($z \in \mathbb{R}^{|V|}$). These logits are converted into probabilities using the Softmax function with Temperature scaling ($T$):

$$P(w_i) = \frac{\exp(z_i / T)}{\sum_{j=1}^{|V|} \exp(z_j / T)}$$
Temperature ($T$) Mathematical Behavior Production Application
$T = 0.0$ (Greedy Decoding) Collapses distribution; top logit gets near 100% probability: $\arg\max_i P(w_i)$. Mandatory for code generation, mathematical extraction, and structured JSON parsing. Completely deterministic.
$T = 0.2 - 0.5$ (Low Temp) Slightly smoothed; highly focused on top tokens with minimal variation. Fact-grounded summarization, customer support chatbots, enterprise RAG synthesis.
$T = 0.7 - 1.0$ (Moderate Temp) Balances diversity and coherence; allows lower-probability tokens to be sampled. Creative writing, marketing ideation, conversational open-ended dialogue.
$T > 1.5$ (High Entropy) Flattens distribution toward uniform randomness. High entropy. Extreme brainstorming; high risk of hallucination and ungrammatical gibberish.

1.4 Persona Steering & The Invariant Facts Principle

When steering models with differing system instructions (e.g., an aggressive/hostile persona vs. an overly polite/empathetic persona), **the underlying factual truth must remain invariant**. Persona modulates *how* information is delivered (cadence, tone), never *what* factual truth is delivered (e.g., store hours must remain identical).

MODULE 5: Reasoning Prompts, Chain-of-Thought & Built-In Thinking (Topic 5)

1. Academic Context & Theoretical Deep Dive

1.1 The Cognitive Mechanism: Why LLMs Need Scratchpad Tokens

Why does an LLM fail when asked: "Calculate total cost for a 450-peso meal with a 15% discount, 12% VAT, and 20-peso voucher. Reply with ONLY the number"?

💡 The Mental Math Analogy: Scratchpads vs. Instant Guesses
If someone asks you to multiply $487 \times 693$ in your head in 1 second, you will guess wrong. But if you have scratch paper to write out intermediate steps, you calculate it easily. An LLM predicts one token at a time with a fixed computational depth per forward pass. Forcing it to output the final number immediately requires it to compute all multi-step math in a single pass. Writing out intermediate reasoning steps stores partial results in its context (KV Cache), giving it dynamic working memory!
DIRECT PROMPT: Prompt: "Solve: (450 * 0.85) * 1.12 - 20. Number only." Forward Pass 1 ──▶ Model forced to guess final number immediately ──▶ HIGH FAILURE RATE REASONING / CHAIN-OF-THOUGHT (CoT) PROMPT: Prompt: "Solve step by step. Show your calculations." Tokens 1-10: "Step 1: 15% discount on 450 is 450 * 0.85 = 382.50." (Enters Context) Tokens 11-20: "Step 2: Add 12% VAT: 382.50 * 1.12 = 428.40." (Attends to Step 1) Tokens 21-28: "Step 3: Subtract 20 voucher: 428.40 - 20 = 408.40." (Attends to Step 2) Tokens 29-32: "ANSWER: 408.40" (Near 100% Accuracy!)

1.2 Prompted Reasoning vs. Built-In Thinking

1.3 Programmatic Delimiter Contracts (ANSWER: <number>)

Humans want step-by-step explanations, but backend code (e.g. checkout carts) will crash if given a paragraph instead of a clean float. We resolve this using a Delimiter Contract: 

Solve the problem step by step and show your calculations.
On the final line, write your answer in this exact format:
ANSWER: <number>

Backend extraction pattern using Python regex:

import re

def extract_numeric_answer(reply: str) -> float | None:
    match = re.search(r"ANSWER:\s*([0-9.]+)", reply)
    return float(match.group(1)) if match else None

1.4 Controlling Reasoning Format via Worked Examples

Embedding a single worked example inside a ChatPromptTemplate establishes a consistent, professional derivation layout across varied problem inputs: 

worked_example = """Problem: A 100-peso item has 10% discount and 12% VAT.
Calculations:
- Discounted price: 100 * 0.90 = 90.00
- Price with VAT: 90 * 1.12 = 100.80
ANSWER: 100.80"""

reasoning_template = ChatPromptTemplate.from_messages([
    ("system", "Solve the math problem. Use the exact layout below:\n\n" + worked_example),
    ("human", "Problem: {problem}")
])

1.5 The Production Shipping Decision: "Which Prompt Would You Ship?"

In industry, prompt engineers do not choose prompts based on accuracy alone. You must balance four competing production dimensions:

  1. Accuracy: Percentage of problem instances solved correctly.
  2. Output Token Overhead: Direct prompt generates ~10 tokens; CoT generates ~150 tokens.
  3. Inference Latency: Generating 150 tokens takes 1.5–3.0 seconds longer.
  4. Token Economics at Scale: At 100,000 requests/month, 150 extra tokens per request equals 15,000,000 additional output tokens.
🎯 Production Decision Formula
"For the checkout calculation feature, we ship the Reasoning (CoT) prompt because it achieved 100% accuracy versus 33% for the Direct prompt. The additional 140 output tokens (~$1.50/month at 100,000 scale) are fully justified to eliminate customer-facing financial billing errors."
